# What I would improve next

## 1. **Fix the validation methodology first**

This is now your biggest weakness.

You select the pair threshold and margin using the validation set:

```text
train entities
      ↓
validation entities
      ↓
threshold search
```

Then your entity gate is also trained/tuned/evaluated from that same validation population. You do split the gate into fitting, tuning, and evaluation portions, which is good, but the underlying pair threshold was already optimized using the complete validation set.  

That means the final reported validation score can still be optimistic.

### Change it to:

```text
                 ALL TRAIN S1
                      │
          ┌───────────┼───────────┐
          │           │           │
       Fold 1      Fold 2      Fold 3 ...
          │           │           │
          ▼           ▼           ▼
        OOF predictions
              │
              ▼
      threshold selection
              │
              ▼
      entity-gate selection
              │
              ▼
       final model training
              │
              ▼
             TEST
```

Even better:

**5-fold entity-level OOF validation.**

Then optimize:

```text
F0.5_entity_macro
```

over all OOF predictions.

This gives you a much more trustworthy threshold.

### Why this matters

You aren't optimizing ordinary pair classification.

Your actual optimization target is:

```text
S1 entity
    ↓
{zero / one / multiple S2/S3 matches}
    ↓
entity-level F0.5
```

So the validation machinery needs to behave the same way.

# 2. **Retrain the final model on ALL training entities**

Currently you split training entities, train the model, then eventually throw away the training objects:

```python
del train_lookup, train_index, train_examples, val_examples
```

and move to test. Your model itself was trained only on the training portion. 

That's useful for honest validation, but after selecting:

```text
features
model family
hyperparameters
threshold
margin
gate architecture
```

you should retrain the **final pair model using all labeled S1 entities**.

Ideal pipeline:

```text
Training data
    │
    ├── CV/OOF → select configuration
    │
    └── ALL training entities
              ↓
        final pair model
              ↓
            TEST
```

The OOF threshold should then be retained or recalibrated carefully.

# 3. **Make LightGBM the main model**

You already added LightGBM support. 

I would now prioritize:

```text
Logistic Regression
        vs
LightGBM
        ↓
OOF entity-F0.5
        ↓
select winner
```

rather than spending time on the MLP.

Why?

Your features contain many nonlinear interactions:

```text
name similarity
        ×
address similarity
        ×
postal agreement
        ×
country
        ×
house number
```

For example:

```text
name = 0.94
address = 0.10
```

is suspicious.

But:

```text
name = 0.94
address = 0.86
postal = exact
house number = exact
```

is extremely different.

Logistic regression has to approximate such interactions linearly unless you manually create the interaction terms.

LightGBM naturally captures this.

# 5. **Replace fixed block-frequency cutoff with adaptive blocking**

You currently have:

```python
--max-block-frequency 10000
```

and blocks above that frequency are ignored. 

That's reasonable, but crude.

Imagine:

```text
"technology" → 80,000 entities
"apollo"     → 4,000 entities
"apollo lab" → 70 entities
```

These should not be treated identically.

A better system:

```text
block rarity
     ↓
IDF
     ↓
block quality
     ↓
weighted retrieval
```

For example:

```text
exact_name        weight = 10
name_pair         weight = 8
rare_name_token   weight = 7
postal            weight = 9
house_number      weight = 6
city              weight = 2
common_token      weight = 0.2
```

Then retrieve top candidates from **each blocking channel separately**.

For example:

```text
top 50 from name
+
top 50 from address
+
top 25 from postal
+
top 25 from house number
+
top 25 from char ngram
```

Then union them.

That is usually safer than one giant union.

retrieval_score =

# 7. **Fix threshold search precision**

Your threshold search currently evaluates quantile-derived thresholds. 

That's better than the old implementation, but still approximate.

You can miss the actual optimum between two quantiles.

Use:

```text
candidate scores
      ↓
sort unique decision boundaries
      ↓
evaluate F0.5 after each boundary
```

Or use a much denser set:

```text
500–2000 thresholds
```

combined with a fast vectorized entity scorer.

More importantly, do it using **OOF predictions**.

# 8. **Your probability margin is not really a probability margin**

You're doing:

```text
candidate probability >= best_probability - margin
```

This is okay operationally, but remember:

```python
class_weight="balanced"
```

is being used in the pair model. 

Therefore the output is not necessarily a well-calibrated real-world probability.

So:

```text
0.05 difference
```

doesn't inherently mean something meaningful.

A better entity-level feature is:

```text
logit(best) - logit(second)
```

or:

```text
score(best) / score(second)
```

or simply:

```text
rank gap
```

For example:

```text
best = 0.94
second = 0.91

vs

best = 0.94
second = 0.35
```

These should behave very differently.

Your entity layer already captures probability gap; I would explicitly add:

```text
logit_gap
relative_gap
top1/top2 ratio
top1-top3 gap
```

# 10. **Add cardinality prediction**

This is one of the most valuable improvements I would make.

The target isn't simply:

```text
match / no match
```

It is:

```text
0 matches
1 match
2 matches
3 matches
...
```

Your challenge explicitly allows an S1 entity to match zero, one, or multiple S2/S3 records. 

So create a second entity-level prediction task:

```text
                         ┌── match/no-match
S1 candidate set ────────┤
                         └── expected cardinality
```

For example:

```text
P(0 matches)
P(1 match)
P(2+ matches)
```

Then your final decision becomes:

```text
entity gate
    +
cardinality estimate
    +
pair scores
    ↓
final set
```

Example:

```text
Predicted cardinality = 1

candidate:
A = 0.97
B = 0.89
C = 0.31

→ A
```

versus:

```text
Predicted cardinality = 2

A = 0.97
B = 0.94
C = 0.90

→ A,B
```

This is much closer to the actual problem.
