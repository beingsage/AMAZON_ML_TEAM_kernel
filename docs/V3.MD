# But I would NOT call this 9/10 yet

There are still some important problems.

## Problem 1 — Your blocking is still potentially dangerous

This part worries me:

```text
name_token
address_token
name_char_ngram
...
```

You union candidates from many blocks.

That's good for recall, but some blocks can become enormous.

You attempted to control that with:

```python
max_block_frequency=10000
```

which is good.

But I would **measure block statistics**:

```text
block type
median candidates
p95 candidates
p99 candidates
max candidates
truth recall
```

For example:

```text
name_exact       recall 98.4%   avg 3.2
postal           recall 91.2%   avg 12
house_number     recall 87.3%   avg 41
char_ngram       recall 99.1%   avg 850
city_token       recall 94.7%   avg 320
```

Then you can know which blocks actually contribute.

---

# Problem 2 — You should NOT optimize only candidate recall

You now measure candidate recall, which is excellent.

But the real chain should be:

```text
Candidate Recall
       ×
Matcher Recall
       ×
Precision
       ↓
Entity F0.5
```

Because your metric strongly rewards precision.

A blocking strategy with:

```text
99.9% recall
```

and

```text
20,000 candidates/entity
```

may be much worse computationally and statistically than:

```text
99.3% recall
```

with:

```text
200 candidates/entity
```

You need a **candidate efficiency curve**.

---

# Problem 3 — Your singleton strategy is still not truly entity-level

This remains one of the biggest weaknesses.

Suppose:

```text
S1-123
```

has **no real match**.

Your system generates:

```text
C1  P=.94
C2  P=.91
C3  P=.88
```

Your matcher may happily return:

```text
C1
```

unless the threshold rejects it.

But the actual decision is:

```text
MATCH SOME RECORDS
          vs
MATCH NOTHING
```

That's an **entity-level decision**, not merely a pairwise classification problem.

I would explicitly add features/logic for:

```text
best_probability
second_probability
probability_gap
number_above_threshold
best_name_score
best_address_score
best_country_score
best_candidate_rank
```

Then learn:

```text
Is this S1 entity linked to anything?
```

separately from:

```text
Which S2/S3 records belong to it?
```

This could substantially improve singleton precision.

# Problem 5 — Your feature engineering has some questionable features

For example:

```python

```

is:

```python
char_similarity(
    " ".join(sorted(name1)),
    " ".join(sorted(name2))
)
```

That's not really **token order similarity**.

Sorting destroys original order.

So this is closer to:

> character similarity after canonical token sorting.

That's actually useful—but the feature name is misleading.

I'd rename it:

```text
name_sorted_token_similarity
```

and add a genuine order-aware feature separately.
