# The biggest thing I found

There is one subtle issue that I would fix before doing more feature engineering.

## 1. Your gate/cardinality validation has a calibration leakage path

Your OOF design itself is good:

```text
S1
 ↓
5 folds
 ↓
OOF pair predictions
 ↓
fold 0 = independent holdout
```

Your model-family comparison also keeps fold 0 separate. 

However, when you construct the entity-level gate features, you take:

```text
folds 1..4
   ↓
fit probability calibrator
   ↓
apply it to folds 1..4
   ↓
use fold 4 as gate-tuning set
```

The calibrator is therefore trained partly on the same fold that is subsequently used to tune the gate/cardinality layer. The code fits the final OOF calibrator from every fold except fold 0, then applies it back onto those same rows. 

That is **not catastrophic**, because fold 0 remains independent, but it means your gate-selection fold is not perfectly nested.

### Better structure

```text
Fold 0                  → FINAL INDEPENDENT TEST OF DESIGN

Fold 1,2,3              → fit gate
Fold 4                  → tune gate threshold

For gate features:
    calibrator = fit on Fold 1,2,3
    apply to Fold 4

Then:
    after architecture is selected
    refit gate on Fold 1,2,3,4
```

That makes the meta-decision stage statistically cleaner.

### Priority

**P0**

# 4. Your retrieval score has one subtle weighting issue

You calculate per-channel scores and then do:

```text
candidate score
=
sum(
    channel score
    +
    context score
)
```

So if a candidate appears in five channels, the same context score is effectively added multiple times.

Conceptually:

```text
Candidate A
postal + name + city
    ↓
context counted 3×

Candidate B
name only
    ↓
context counted 1×
```

This intentionally rewards multi-channel agreement, but it mixes two separate concepts:

```text
retrieval evidence
+
channel multiplicity
```

I'd redesign this as:

```text
retrieval_score =
    Σ channel_score
    +
    context_score_once
    +
    agreement_bonus
```

rather than repeatedly adding the same context term.

This is not necessarily wrong, but it is worth an ablation because it can distort ranking.

# 5. Your cross-source graph is excellent — but watch transitive contamination

This is one of the strongest additions.

You're building S2↔S3 relationships and unioning connected components. 

Conceptually:

```text
S2-A ───── S3-A
           │
           │
           ▼
         S2-B
```

becomes one cluster.

That's useful.

But union-find creates **transitive closure**:

```text
A ↔ B
B ↔ C

therefore

A ↔ C
```

even though A↔C was never directly verified.

This can be dangerous with:

* franchises,
* businesses sharing buildings,
* repeated company names,
* businesses with identical normalized names.

### Improvement

Don't make cluster membership binary only.

Instead store:

```text
direct_edge_count
max_edge_score
min_edge_score
average_edge_score
strongest_name_similarity
strongest_address_similarity
number_of_opposite_source_records
cluster_size
```

Then the model can distinguish:

```text
strong 2-node cluster
```

from:

```text
large weak transitive cluster
```

# 6. Cardinality is good, but it is still relatively coarse

You now explicitly model:

```text
0
1
2+
```

which is a very good direction.

The code then modifies the pair predictions according to the predicted cardinality. 

The remaining problem is that your `2+` policy is still partly heuristic:

```text
second probability >= threshold - 0.1
and
within margin
```

That `0.1` is manually chosen.

I'd turn this into a learned/tuned policy:

```text
P(cardinality=0)
P(cardinality=1)
P(cardinality=2+)

then optimize:

k threshold
score threshold
margin
```

on the tuning fold.

Even better:

```text
cardinality class
      ↓
class-specific selection rule
```

For example:

```text
0 → empty
1 → top1 if score > T1
2+ → all candidates above T2 and margin M2
```

instead of a single universal pair threshold.

# 7. Your final calibration becomes slightly stale after adversarial retraining

This is subtle and important.

You do:

```text
OOF models
   ↓
calibrator
   ↓
threshold
```

Then later:

```text
fit final model
   ↓
mine new adversarial negatives
   ↓
refit final model
```

but you retain:

```text
selected_oof.probability_calibrator
```

for the newly refitted model.  

So the raw score distribution has changed:

```text
OOF model
   ↓
calibrator A

FINAL model + extra hard negatives
   ↓
calibrator A
```

That calibration is no longer guaranteed to be exact.

### Two clean approaches

**Option A — simpler**

Do not perform the second final adversarial retraining after calibration.

Keep:

```text
OOF-selected training composition
→ final fit
→ OOF calibrator
```

consistent.

**Option B — stronger**

Run a second OOF calibration pass using the final training recipe.

More computationally expensive, but statistically cleaner.

I'd test A first.
